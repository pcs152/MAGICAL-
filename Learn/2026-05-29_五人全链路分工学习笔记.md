# 2026-05-29 五人全链路分工学习笔记

## 1. 总体原则

五个人不应该都挤在“跑版图”这一件事上。更合理的分工是沿着模拟 IC 自动化设计全链路拆开：

```text
用户需求
-> 前端拓扑与网表生成
-> 参数优化与前仿
-> Harness 约束调度
-> MAGICAL 候选版图生成
-> DRC / LVS / PEX
-> 寄生提取与后仿差异分析
-> 回退到前端或后端修正
-> 最终 GDS 交付
```

每个人负责一个可以独立推进、又能在接口上串起来的模块。这样既能形成工程闭环，也能让每个人都有可包装成论文或比赛亮点的方向。

## 2. 建议的五人角色

### 2.1 前端生成负责人：需求到拓扑、网表和测试平台

核心职责：

- 接收用户需求和电路指标。
- 生成或选择电路拓扑。
- 生成 SPICE 网表。
- 生成 testbench。
- 调用或改造 AnalogCoder / AnalogCoder-Pro 类前端工具。

输入：

```text
用户需求
电路指标
拓扑约束
工艺与电源条件
```

输出：

```text
标准化 SPICE 网表
测试平台 testbench
电路拓扑描述
初始参数范围
```

和其他人的接口：

- 给参数优化负责人提供 topology、netlist、testbench、参数边界。
- 给 Harness 提供前端生成日志和候选设计版本。
- 接收 Harness 回退信号，例如“拓扑不合适”“器件映射语义不足”“需要调整关键节点设计余量”。

论文/亮点方向：

```text
LLM 辅助模拟电路拓扑生成与测试平台构建
```

注意：

这个方向竞争比较激烈，已有 AnalogCoder、AnalogCoder-Pro、ChatEDA、AnalogMaster 等工作。因此如果单独发论文，需要非常明确的新贡献；否则更适合作为系统上游模块。

### 2.2 参数优化负责人：GRPO / sizing / 前仿评估

核心职责：

- 接收前端给出的 netlist、testbench 和参数范围。
- 优化晶体管尺寸参数，例如 W/L/M/nf。
- 运行前版图仿真。
- 生成多组候选参数。
- 将性能指标回传给 Harness。

输入：

```text
SPICE 网表
testbench
参数搜索空间
目标指标
约束条件
```

输出：

```text
候选参数集
前仿性能指标
候选设计排序
优化日志
```

关键指标：

- 增益。
- 带宽。
- 相位裕度。
- 功耗。
- 面积估计。
- 工作点。

和其他人的接口：

- 接收前端生成的 netlist 和 testbench。
- 将候选设计交给 MAGICAL 后端负责人。
- 接收寄生提取负责人和 Harness 的反馈，例如“输出节点寄生风险高”“偏置点漂移”“需要增加某类指标裕量”。

论文/亮点方向：

```text
面向模拟电路的 GRPO 参数优化与多候选 sizing
```

注意：

如果只是把师兄已有 GRPO 工具接进来，创新性可能不够。更强的论文方向是把后端反馈、寄生风险或后仿退化信息加入优化目标。

### 2.3 Harness 负责人：约束检查、流程调度和失败归因

核心职责：

- 定义全流程状态机。
- 定义每一步的约束和验收标准。
- 判断流程是否继续、回退或终止。
- 根据失败类型决定回前端、回参数优化、回版图生成，还是回器件映射。

输入：

```text
前仿指标
MAGICAL 运行日志
DRC / LVS 结果
PEX 寄生摘要
后仿指标
前后仿差异
```

输出：

```text
流程状态
失败归因结果
回退决策
下一步任务
可追溯日志
```

Harness 的“度”：

- 前仿是否满足目标。
- 前仿是否有合理裕量。
- 后仿是否满足目标。
- 前后仿退化比例是否可接受。
- DRC / LVS 是否通过。
- 关键网络寄生是否过大。
- 工作点是否漂移。
- 功耗、面积、稳定性代价是否可接受。

典型决策：

```text
DRC 失败 -> 回后端版图约束或工艺映射
LVS 失败 -> 回网表映射、端口或器件连接
工作点漂移 -> 回参数优化或偏置设计
关键网络寄生过大 -> 回版图布局布线
nf / matching / symmetry 异常 -> 回器件映射和约束提取
系统性后仿退化 -> 引入寄生感知前端模型
```

和其他人的接口：

- 从所有模块收集结果。
- 给所有模块发出下一步指令。
- 负责保存每个候选设计的版本、指标和失败原因。

论文/亮点方向：

```text
面向模拟 IC 自动化设计的约束驱动 Harness 与失败归因机制
```

注意：

这是系统中枢，论文潜力高，但工程难度也最大。它需要其他模块有稳定输入输出，否则容易变成空架构。

### 2.4 MAGICAL 后端负责人：候选版图生成与物理验证基线

核心职责：

- 维护 MAGICAL Sky130 后端流程。
- 完成候选版图生成。
- 跑通 DRC、LVS、PEX。
- 保证 inverter、OTA 等 baseline 可复现。
- 管理 PDK 映射、层映射、pin 处理和工具链环境。

输入：

```text
标准化网表
端口信息
电源地网络
后端配置
版图约束
```

输出：

```text
MAGICAL 候选版图
DRC 报告
LVS 报告
PEX 提取网表
运行日志
候选版图相关中间文件
```

重要原则：

- MAGICAL 生成的是候选版图，不是最终 GDS。
- 最终 GDS 只能在 DRC、LVS、PEX 和后仿全部满足后确认。
- 后端负责人主要保证工程基线稳定，不宜把所有创新都压在改 MAGICAL 内部算法上。

和其他人的接口：

- 从参数优化负责人接收候选设计。
- 向寄生提取负责人输出 PEX 结果和带寄生网表。
- 向 Harness 输出 DRC、LVS、PEX 状态。
- 接收 Harness 的后端回退决策，例如“关键网络寄生过大”“器件连接不一致”“需要修正 pin 或 layer remap”。

论文/亮点方向：

```text
基于 MAGICAL 的 Sky130 开源模拟版图生成与验证基线
```

注意：

这个方向工程价值很高，但单独作为论文创新点不一定最强，因为 MAGICAL / ALIGN 已经是成熟方向。它更适合做全系统的后端支撑。

### 2.5 寄生提取与反馈负责人：PEX 结构化、后仿差异和前后端诊断

核心职责：

- 从 Magic / MAGICAL 的 PEX 结果中提取寄生参数。
- 生成结构化 `parasitic_summary.json`。
- 标记关键网络和高风险寄生。
- 比较前仿和后仿差异。
- 给 Harness 提供“问题可能回前端还是回后端”的诊断依据。

输入：

```text
PEX summary
带寄生提取网表
后仿结果
前仿结果
电路关键节点信息
```

输出：

```text
parasitic_summary.json
关键网络排名
单网络电容统计
寄生风险分析
前后仿退化分析
前端/后端修正建议
```

需要回答的问题：

```text
哪个节点寄生最大？
哪个节点是关键网络？
寄生是否足以解释后仿退化？
性能退化更像是版图太重，还是前端设计太怕寄生？
应该回前端 sizing，还是回后端布局布线？
```

典型诊断：

```text
关键网络寄生异常大 -> 更可能回后端布局布线
寄生不算大但性能崩 -> 更可能回前端 sizing 或偏置设计
差分两边寄生不对称 -> 可能回 matching / symmetry 约束
多个候选都后仿崩 -> 需要寄生感知前端模型
```

和其他人的接口：

- 接收 MAGICAL 后端负责人的 PEX 输出。
- 接收参数优化负责人的前仿结果。
- 输出结构化诊断给 Harness。
- 必要时给前端优化负责人提供寄生风险惩罚项或动态设计裕量建议。

论文/亮点方向：

```text
面向模拟 IC 自动化设计闭环的寄生参数提取与前后端反馈建模
```

这是最适合覃林峰当前切入的方向。它不需要从零做 PEX 工具，而是把真实 PEX 结果变成 Harness 和前端优化器能使用的反馈信号。

## 3. 五个人之间的数据接口

建议用统一的数据流串起来：

```text
design_spec.json
-> frontend_netlist.sp
-> testbench.sp
-> candidate_sizing.json
-> prelayout_metrics.json
-> magical_case_config.json
-> drc_lvs_report.json
-> parasitic_summary.json
-> postlayout_metrics.json
-> harness_decision.json
```

其中最关键的接口是：

- `candidate_sizing.json`：参数优化交给后端。
- `prelayout_metrics.json`：前仿结果交给 Harness。
- `parasitic_summary.json`：寄生提取负责人交给 Harness。
- `postlayout_metrics.json`：后仿结果交给 Harness。
- `harness_decision.json`：Harness 决定下一步回哪里。

## 4. 推荐的一周内最小闭环

不建议一开始就做完整系统。第一周可以只做最小闭环：

```text
固定 inverter / OTA case
-> 使用已有 MAGICAL pipeline
-> 生成 PEX summary
-> 转成 parasitic_summary.json
-> 和后仿或已知性能指标对齐
-> Harness 输出一个简单判断：
   通过 / 回前端 / 回后端 / 需要人工检查
```

这样五个人都能接入：

- 前端负责人：准备标准 netlist / testbench。
- 参数优化负责人：准备候选参数格式。
- 后端负责人：跑 MAGICAL baseline。
- 寄生负责人：输出 `parasitic_summary.json`。
- Harness 负责人：读所有 JSON，输出决策。

## 5. 最重要的分工结论

五个人的分工应该是：

```text
前端生成：负责需求、拓扑、网表、testbench
参数优化：负责 sizing、前仿、多候选搜索
Harness：负责约束、调度、失败归因和回退决策
MAGICAL 后端：负责候选版图、DRC、LVS、PEX 工程基线
寄生提取：负责 PEX 结构化、后仿差异和前后端反馈建模
```

这样分工的好处是：

- 每个人都有清晰产物。
- 每个人都能独立推进。
- 每个模块都有论文或比赛亮点。
- 最终可以串成一个完整的前后端闭环系统。

## 6. 环境 Harness 的一次关键经验

这次 DFCFC2 / MIM proxy 后端验证暴露了一个很重要的问题：不能只说“装了 Magic / PDK / Docker”，必须固定一套可检查的环境入口。

正确做法是：

```text
source scripts/env/magical_sky130_env.sh
-> 固定 PDK_ROOT / SKY130A / Docker image
-> 固定 magic wrapper
-> 自动检查 Magic 版本和 PDK hash
-> pipeline 每次运行前自己检查，不靠人记忆
```

这件事很适合作为后续环境 Harness 的基础。

本次结论：

- 裸宿主机 `magic` 曾经是 `8.3.105`，会和当前 sky130A techfile 不兼容。
- 固定环境后，`magic` 走 `/home/qlf/IOT/scripts/env/bin/magic`。
- wrapper 中的 Magic 版本是 `8.3.483`，满足当前 sky130A techfile 的要求。
- `scripts/env/check_magical_sky130_env.sh` 可以检查 Docker、Magic、PDK hash、sky130A magicrc、netgen setup 等关键条件。
- `run_sky130_case_pipeline.sh` 现在会主动 source 固定环境，并且要求 `Magic >= 8.3.411`。

固定环境后的真实结果：

```text
MAGICAL placement/routing：可以进入后端
Magic DRC：通过，DRC_COUNT=0
Magic extraction / PEX：通过
PEX capacitor count：103
total parasitic capacitance：865.01 fF
vout parasitic capacitance：363.423 fF
connectivity LVS：失败
Harness decision：reject_pipeline_artifact
```

这说明环境问题已经从“跑不起来”变成了“能跑到真实后端诊断”。剩下的问题不是 Magic 版本，而是 DFCFC2 的 MIM proxy / LVS / gnda 连接一致性问题。

这也给后续 Harness 一个原则：

```text
环境问题要早失败；
真实工具问题要留下结构化报告；
DRC/PEX 能跑不代表样本可用；
只有 LVS/约束/寄生诊断都过，才能进入最终样本或后仿闭环。
```
